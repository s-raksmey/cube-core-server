# Article editorial workflow

Articles belong to one SUB tenant and use the tenant application's existing permission system. The default language is English in `Article`; optional languages live in `ArticleTranslation`. An article and all its translations share one status. Article tags use the existing tenant-scoped join table. Category, subcategory, and tag IDs are checked against the session tenant, and composite foreign keys protect the category/subcategory pair and tag association.

The supported statuses are `DRAFT`, `IN_REVIEW`, `SCHEDULED`, `PUBLISHED`, and `ARCHIVED`. The transition policy is in `src/modules/articles/article-policy.ts`. Only drafts allow normal content updates, even for users with `ARTICLE_UPDATE_ANY`. A published article can return to Draft only through `unpublishArticle` with `ARTICLE_UNPUBLISH`; scheduled content requires schedule cancellation, and in-review content requires a changes request. Breaking, Featured, and Archive also require Draft, so a published article must be unpublished first. Restore returns an archived article to Draft; publishing it again requires the usual Publish or review workflow. Dedicated GraphQL mutations enforce each transition and permission. Review submissions, changes requests, and decisions append history records. Hard deletion is limited to Draft through `deleteArticle` or Archived through `deleteArchivedArticle`; the archived path requires the separate `ARTICLE_DELETE_ARCHIVED` permission and writes an `ARTICLE_PERMANENTLY_DELETED` audit event in the same transaction. Deletion cascades to article-specific translations, tags, and review history; shared categories, tags, users, and media remain intact.

Scheduling stores an absolute timestamp in the database. The tenant UI labels its date/time entry **UTC** and sends an ISO timestamp with an explicit `Z` offset. The GraphQL service accepts ISO timestamps with an offset and rejects past times. The long-running GraphQL server starts a scheduler at boot and scans durable database state every 30 seconds, including immediately after startup. Each due publication uses a conditional update on status and scheduled timestamp in a transaction, so multiple server instances cannot publish or audit the same article twice. The scheduler processes 100 due articles per scan; backlogs drain over subsequent scans. A continuously running server process is required for timely publication. After downtime, overdue articles publish on startup.

The existing tenant Media page has no upload or asset-selection implementation. Article editing therefore accepts an HTTPS featured-image URL and Markdown image links. It does not create a separate media store. Markdown HTML is rejected at input and the authenticated preview sanitizes rendered content.

The public website resolves its active SUB tenant from the request hostname (or the configured local-development tenant). Its separate GraphQL reads accept that resolved tenant ID and recheck active tenant status. Public lists, category/topic navigation, search, tags, and detail reads select only `PUBLISHED` articles with `publishedAt` no later than the current server time. They use explicit Prisma projections and bounded pagination; draft, review, scheduled, and archived content never enters a public response. Public URLs follow `/category/topic/article-slug`.

`publicWebsiteCategories` returns the active tenant's configured categories and subcategories, including empty sections so navigation and archive routes work before the first publication; `publicWebsiteTags` returns tags attached to published articles. `publicWebsiteArticles` applies category, subcategory, tag, search, featured, and breaking filters within the active tenant. The public website resolves tenant identity and calls these read operations on the server, while tenant-managed branding assets are served through a same-origin website rewrite.

The migration grants the new Article permissions to existing global built-in `ADMIN` and `EDITOR` roles with conflict-safe inserts. Since these permission codes did not exist before the migration, existing permission choices are otherwise preserved. The seed supplies the same defaults when a role has no permissions yet; it does not regrant Article permissions after later customization. Admin receives all Article permissions. Editor receives view, create, update own, delete own, and submit. Existing Editor category, subcategory, and tag view defaults remain in place.

The follow-up Unpublish migration grants only the new `ARTICLE_UNPUBLISH` code to the built-in Admin role, including existing installations, without changing other role permissions. Editor does not receive it by default, but the role permission matrix may explicitly grant it. `publishedAt` records the most recent publish time: unpublishing preserves it as history, while republishing (including scheduled publication) replaces it with the new publication time. Public reads require `PUBLISHED` status, so unpublishing or archiving removes articles from public lists and detail immediately. Breaking and Featured remain separate permissioned Draft presentation actions and do not unlock editorial content in other statuses.

The archived-delete permission migration uses the same conflict-safe strategy: built-in Admin receives `ARTICLE_DELETE_ARCHIVED` on existing installations, Editor does not receive it by default, and unrelated custom role permissions remain unchanged. The Roles & Permissions matrix can grant it explicitly. Permission checks never rely on the role name.

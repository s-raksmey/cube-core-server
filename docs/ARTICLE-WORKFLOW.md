# Article editorial workflow

Articles belong to one SUB tenant and use the tenant application's existing permission system. The default language is English in `Article`; optional languages live in `ArticleTranslation`. An article and all its translations share one status. Article tags use the existing tenant-scoped join table. Category, subcategory, and tag IDs are checked against the session tenant, and composite foreign keys protect the category/subcategory pair and tag association.

The supported statuses are `DRAFT`, `IN_REVIEW`, `SCHEDULED`, `PUBLISHED`, and `ARCHIVED`. The transition policy is in `src/modules/articles/article-policy.ts`. Dedicated GraphQL mutations enforce each transition and permission. Review submissions, changes requests, and decisions append history records. Workflow changes and audit events commit together. Draft deletion is the only hard-delete path; published content is archived.

Scheduling stores an absolute timestamp in the database. The tenant UI labels its date/time entry **UTC** and sends an ISO timestamp with an explicit `Z` offset. The GraphQL service accepts ISO timestamps with an offset and rejects past times. The long-running GraphQL server starts a scheduler at boot and scans durable database state every 30 seconds, including immediately after startup. Each due publication uses a conditional update on status and scheduled timestamp in a transaction, so multiple server instances cannot publish or audit the same article twice. The scheduler processes 100 due articles per scan; backlogs drain over subsequent scans. A continuously running server process is required for timely publication. After downtime, overdue articles publish on startup.

The existing tenant Media page has no upload or asset-selection implementation. Article editing therefore accepts an HTTPS featured-image URL and Markdown image links. It does not create a separate media store. Markdown HTML is rejected at input and the authenticated preview sanitizes rendered content.

The migration grants the new Article permissions to existing global built-in `ADMIN` and `EDITOR` roles with conflict-safe inserts. Since these permission codes did not exist before the migration, existing permission choices are otherwise preserved. The seed supplies the same defaults when a role has no permissions yet; it does not regrant Article permissions after later customization. Admin receives all Article permissions. Editor receives view, create, update own, delete own, and submit. Existing Editor category, subcategory, and tag view defaults remain in place.

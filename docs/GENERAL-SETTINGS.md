# Sub-tenant General settings

General settings reuse the existing `Tenant.settings` JSON column under the `general` key. There is no separate settings table. Existing tenants without this key read a safe default: the tenant name for `siteName`, empty text for other fields, and `null` for `secondaryPhone`.

The tenant console reads `myGeneralSettings` and updates `updateMyGeneralSettings(input)`. Both take tenant identity only from the authenticated `TENANT_APP` session. `SETTINGS_VIEW` and `SETTINGS_UPDATE` are independent role permissions; updates also require the standard active tenant membership. The General input is strict and validated by Zod. Other settings keys are preserved on update.

The public `publicGeneralSettings(hostname)` query resolves an active website domain with the existing hostname mapping. In development, `localhost` uses the selected local tenant. It returns only the six General fields plus public-safe `website` and `socialLinks` fields, never the management settings JSON. The public website consumes the site name and description for its visible identity and metadata.

Website maintenance settings live under the `website` key in the same JSON column. `myWebsiteSettings` and `updateMyWebsiteSettings(input)` use the same authenticated tenant and `SETTINGS_VIEW` / `SETTINGS_UPDATE` permissions. Existing tenants default to `maintenanceMode: false` and `maintenanceMessage: null`. Saving OFF retains the message. Mode transitions write `tenant.website.maintenance.enabled` or `.disabled` to the audit log in the same transaction as the settings update. Message-only saves do not emit a mode-transition event.

The public `website` object contains only `maintenanceMode` and `maintenanceMessage`. The website checks it before rendering content, on every public route, and on client navigation. Tenant resolution fetches with `cache: "no-store"`, and the website refreshes an open tab every 30 seconds (15 seconds during maintenance) and when it becomes visible. No maintenance check runs in either management console or its GraphQL operations.

Social Links use the normalized `TenantSocialLink` relation with one row per tenant/platform. `mySocialLinks` and `updateMySocialLinks(input)` use the authenticated tenant and the same Settings permissions. The bulk save accepts up to seven controlled platforms; an empty disabled URL deletes that row. URLs must be HTTPS and belong to a recognized domain for their platform. Public `socialLinks` resolves under the existing hostname-based config, selects only enabled links, and orders by `sortOrder` then platform. The public website footer uses these tenant links and never embeds fixed social URLs.

SEO defaults live under the `seo` key in the same settings JSON. Existing tenants default to indexing allowed and blank metadata fields. `mySeoSettings` and `updateMySeoSettings(input)` use the authenticated tenant and the same Settings permissions. Inputs are strict and validated by Zod. The public `seo` object is resolved under the existing hostname-based configuration and exposes only public-safe metadata values and a resolved image URL.

The Media page is currently a placeholder and there is no Media model. The SEO tab therefore reuses the existing tenant-owned Open Graph branding image upload and storage. `updateMySeoImage` accepts image bytes for the authenticated tenant, not a Media ID or tenant path. Only a raster PNG, JPEG, or WebP image under that tenant's branding path is returned in public SEO configuration. This image is also available in Website branding settings.

The public website applies article-specific SEO (when present), then article title/summary/featured image, then tenant SEO defaults, then General site name/description and the site image. Empty OG text falls back to meta text. Disabled indexing emits `noindex, nofollow`; unavailable, maintenance, and unpublished article routes remain non-indexable. The public configuration uses uncached tenant resolution so setting changes propagate on the next request.

Content settings live under the `content` key in the same JSON column. `myContentSettings` and `updateMyContentSettings(input)` use the authenticated tenant and `SETTINGS_VIEW` / `SETTINGS_UPDATE`. The default is 24 hours; the input accepts positive whole hours or days up to 30 days. The Content tab changes only the default. It does not grant Article Breaking or publishing permissions.

An Article's `breakingExpiresAt` is set when it becomes Published: immediate publication uses the current time, and scheduled publication uses the scheduler's actual publication time. Unpublishing clears the expiration, so a later publication uses the then-current tenant default. Changing Content settings does not update already-published Articles. Public Breaking reads require a Published article with `isBreaking` and a future `breakingExpiresAt`; other public cards report an expired story as non-Breaking without changing its stored `isBreaking` flag. The migration backfills existing Published Breaking articles with a 24-hour window from their `publishedAt` time.

The Settings screen keeps one sidebar item. General, Website maintenance, Social Links, SEO, and Content are implemented; Website also hosts the existing branding controls.
